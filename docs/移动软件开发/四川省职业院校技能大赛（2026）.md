## 一、解决的核心问题

中职学生"没有好题或原创优质题可练"，根子不在学生，而在**题源的生产与流转方式**。我们调研到的五个真实痛点，就是产品的五个发力点：

| #   | 中职教育现状的真实痛点                                                 | 本产品的解法                                                                                                                                   |
| --- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **优质题源散落各校、无法共享**：好题锁在某位老师的电脑里、某个学校的群里，换了学校就归零，同一个知识点全市反复造题 | 建**全市共享题库**：一道题入库、全市学校可见可组卷；按「公共学科 / 专业大类 / 专业 / 课程」四层知识树组织，各校在同一棵树上共建，越用越厚                                                              |
| 2   | **质量参差、无人把关**：错题错答案直接进学生练习册，口头教研形同虚设                        | **两级审批**（学科教研组长 → 市级专家）通过才入库；改版必须重新审批，历史版本全留痕——谁出的、谁审的、什么时候审的都可追溯                                                                        |
| 3   | **纸质卷 / Word 转成数字题是纯人力活**：一套卷手录一天，还常错行、漏答案、断行               | **AI 整卷导入**：上传 PDF / Word / 拍照扫描件（扫描全能王APP），自动切页、识别题型与选项、抽取答案和解析、合并跨页被切断的题、卷内去重、与库里已有题查重，教师只做「校对 + 勾选」                                   |
| 4   | **出题、组卷、考试、讲评各用一套工具**：Word 排版、手动算分、Excel 排行、讲评靠投屏念          | **全链路闭环**：题库 → 拖拽组卷（自动算分、导出标准 PDF 卷与独立答案页）→ 下发考试（客观题自动判分）+ 手工评分板 → 排行榜 → 讲评大屏（一题一屏）→ 易错题 → 针对性练习                                         |
| 5   | **学情数据靠手工统计、到不了学生手里**：考完只有一张分数表，学生不知道自己差在哪                  | **数据自动回流**：班级报告、选项分布、易错题、四档排行榜（全班·全校·全市·全省）、AI 班级诊断报告；学生端同步看到自己的正确率、错题本、科学抽题练习、遗忘曲线（ 艾宾浩斯记忆曲线揭示了人类遗忘的规律：遗忘速度先快后慢，通过科学复习可以显著延缓遗忘，提高记忆效率。） |

## 二、网站（教师 / 管理端 · Next.js）的特点与亮点

1. **AI 整卷导入，把"存量卷子"变成"数字题库"**
   浏览器里直接打开 PDF / Word / 拍照的试卷，自动分页、识别题型与选项、抽取答案和解析；被分页切断的题自动接上、同一套卷里重复的题自动去掉，再和题库里已有的题比对，相似度高的会提醒（分三档：高度相似 / 较相似 / 仅供参考），避免"撞题"。
   **密钥与费用都不经过本站**：每位教师填自己的 AI 密钥，请求从浏览器直接发给大模型，网站既不保存密钥、也不替大家付钱；多个标签页同时解析会自动排队，中途断开可以接着做。
2. **两级审批 + 多人协同组卷，多校协作有秩序**
   教研组长、市级专家各审一道关，一键流转、一键入库；市级专家还能把一份卷子按"大题里的题号区间 + 目标分"分给几位老师一起出，多人同时编辑不会互相覆盖。审批记录、操作日志、题目纠错、用户反馈都能查。
3. **试卷能直接印**
   一键导出标准试卷 PDF：中文自动换行、行首不会出现标点、答案单独成页（正卷里看不到答案），还能打讲评大屏（一题一屏）；分值支持按题 / 按空 / 按小问三种算法，三道空的填空题不会算错分。
4. **学情分析能落地**
   不只给一个平均分：每道题的选项分布与错误率、每个知识点的掌握度、每个学生的答卷和失分点都有；AI 按班生成分析报告，学生用"学生 1、学生 2"匿名编号，喂给模型的数据里没有任何姓名。
5. **教务与资料中心一体**
   城市 / 学校 / 班级 / 科目树 / 标签 / 用户 / 审批 / 审计日志 / 反馈九个后台页面，学校与权限都能自助维护；复习资料区可传整本教材、整套卷子（单份最大 2GB），学生端能直接在软件里打开。

## 三、软件（学生端 · Flutter，Windows + Android）的特点与亮点

1. **一端开发、两端可用**：同一套 Flutter 代码出 Windows 与 Android 安装包——机房电脑、宿舍笔记本、随身手机都能练，手机竖屏与 1280×800 桌面窗口都做了适配。
2. **四种用法，按需选择**：即时练习（做完立刻看对错和解析）、整卷练习（做完一次交卷）、顺序练习（不记成绩，主要给老师讲练用）、背题模式（只翻卡不答题，专门记知识点）。
3. **越练越懂你**：错题自动进错题本、可以收藏，遗忘曲线按时间告诉你"今天该复习哪几题"，还有每日趋势与学习热力图。
4. **考试和平时一样顺手**：按试卷时间作答，草稿存在本机、断网不丢；交卷立刻出分与排名，能看到整卷每道题的选项分布、自己排第几；考试记录随时可以回看。
5. **内置 AI 答疑**：做题时直接问 AI，不用切出去（Windows 端不需要手机号收验证码；学校规定不能带手机，所以在机房电脑上就能用）。
6. **下载与更新不折腾**：资料、试卷 PDF 可以下载后重复使用；打开软件自动检查新版本；安装包放在国内云存储（实测 7~9.6MB/s），APK 另提供 GitHub 镜像，下载页印了文件校验码（SHA-256）供核对。
7. **工程质量可查**：单个代码文件不超过 200 行、分层清晰，用项目自研的检查脚本自动把关；62 个自动化测试文件 + 6 个端到端测试；GitHub Actions 一键产出正式签名的 Windows 安装包与 Android APK。

## 五、核心卖点（对外推广直接用）

1. **一套系统顶三套**：题库管理 + 组卷考试 + 学生刷题客户端，不需要再拼 Word、Excel、多个刷题 App。
2. **AI 把存量卷子一次搬进数字世界**：原先"一套卷录一天"的活儿变成"十几分钟校对一遍"，学校已有的题源立刻可用。
3. **越用越厚、越用越准**：多校共建 + 两级审核 + 查重防撞题，题量和质量同时滚雪球，而不是各校各出一遍。
4. **学生真的愿意用**：即时判分与解析、排行榜、错题本、遗忘曲线、Windows/Android 都能用——刷题不再是枯燥的纸面作业。
5. **学校零门槛落地**：一所学校就能自建自用，多校加入自动形成联盟；托管在云服务上，无需自购服务器、无需专职运维。
6. **数据安全可控**：答案与正卷分离、AI 密钥不入库、操作全程审计、AI 报告全部匿名——能过学校与教研部门的合规审查。

## 六、落地方案（三步）

1. **建库**：学校管理员开通学校、班级与科目树；教师把本校存量的 PDF / Word 试卷批量导入，学科教研组长、专家审核入库。
2. **用起来**：教师按知识点组卷 → 下发班级 → 学生在 Windows 或 Android 端考试/练习 → 教师看报告与排行 → 讲评课投屏讲易错题。
3. **连成联盟**：多所学校加入同一题库，题目与学情按权限互相可见，形成"市级优质题池"。

## 项目经理：金子轩

### 1. 岗位职责（企业级项目流程：从立项到复盘）

本项目是一个**真实上线**的教育系统：网站 myquiz.cn（教师/管理端）+ Windows/Android 学生端 + Supabase 数据库。客户是一线教师，真实用户是中职教师与学生。所以项目经理不是"催进度的人"，而是**对最终交付结果负责的人**——需求、范围、计划、协作、质量、风险、交付、复盘，八件事一件都不能少。

#### 1.1 立项与需求管理

| 要做的事      | 具体做法（本项目）                                                                | 交付物                         |
| --------- | ------------------------------------------------------------------------ | --------------------------- |
| 需求采集      | 与客户（老师）多轮沟通，把"中职学生没有好题可练"翻译成可开发的需求                                       | 需求池（飞书多维表格 / GitHub Issues） |
| 角色与场景梳理   | 梳理 6 类角色：系统管理员、学校管理员、教研组长、市级专家、教师、学生；梳理核心链路「出题 → 审批 → 组卷 → 考试 → 练习 → 讲评」 | 用户角色图谱 + 业务流程图              |
| 需求文档（PRD） | 每个功能写清「谁、在什么场景、解决什么问题、验收标准」，例如"两级审批：组长流转、专家入库"                           | PRD（含验收标准）                  |
| 需求评审      | 组织客户 + 开发 + 美工 + 测试四方评审，确认唯一口径，避免"开发完才发现不是客户要的"                          | 评审纪要 + 确认记录                 |

#### 1.2 范围与优先级（取舍）

- **MVP 排序**：先打通「题库 + 两级审批 + 学生刷题」，再上「组卷考试 + 学情分析 + AI 报告」。
- **明确写"本期不做"清单并说明理由**。真实案例：教学动画功能做完 M0–M4 后，判断"制作放在本站会加大复杂度"整体砍掉——PM 的价值一半在加需求、一半在砍需求，每次砍单都要留决策记录，避免反复。
- **需求变更走变更流程**：影响哪些功能、影响几天工期、是否影响比赛演示，记录在案后再改。

#### 1.3 计划与里程碑

- 按赛项四模块排期：**原型设计（Figma）→ 界面实现 → 功能开发 → 自动化测试**，每个阶段都有可见交付物（设计稿 / 可运行页面 / 可安装包 / 测试报告）。
- 里程碑验收口径（本项目真实可查）：网页端 `npm run build` 通过；Flutter 端 `flutter analyze` 零 error + `dart run tool/check_architecture.dart` 通过 + 单元测试通过；能打出签名 APK 与 Windows 安装包；下载页三个资产名与发布产物逐字一致。
- 维护任务看板：需求 → 任务 → 负责人 → 截止日 → 状态，每周更新进度与风险。

#### 1.4 团队协作

- **每日站会 15 分钟**（昨天做了什么 / 今天做什么 / 卡在哪），每周一次协作复盘。
- 明确边界：陈明霖负责 Flutter 客户端与 Supabase 后端（数据库、接口、权限）；赵文俊负责 Next.js 网站；美工负责原型与设计系统；自动化测试与 CI/CD 由 AI / 工具承担；PM 负责接住"人工判断"的部分（验收、优先级、口径）。

#### 1.5 质量与验收（UAT）

### 3. 我们的选择之一：Figma（人看的设计：原型、评审、标注）

1. **Windows 可用、免安装**：浏览器直接打开，机房电脑也能用，不占用本机性能（本项目开发机为 Windows，Sketch 仅限 macOS，直接被排除）。
2. **多人实时协作**：项目经理、美工、开发人员可同时在一个文件里看稿、评论、改稿，与"客户（尹老师）多轮沟通修改"的赛项要求天然契合；评论可以直接钉在具体元素上，避免"截屏 + 微信描述"。
3. **组件化与自动布局**：设计稿按组件（按钮 / 卡片 / 列表项 / 输入框）维护，改一处全站生效——这正是本项目 Flutter 端与网页端都能落地的关键（两端都是组件化实现）。
4. **开发可直接取用**：Figma 的 Dev Mode 能查看间距、字号、颜色与导出切图，开发人员不需要再猜"这里是 12 还是 16"。
5. **教育免费 + 插件生态**：学生教育版免费；图标、中文排版、批量切图等插件齐全。

### 4. 我们的选择之二：Open Design（AI 驱动，直接产出代码）

> 定位差别：**Figma 管"人看的设计"**（原型、评审、标注、切图）；**Open Design 管"机器能落地的设计"**（设计系统 → 可运行的前端代码）。两者不重复，是接力关系。

[Open Design](https://github.com/nexu-io/open-design) 是开源的 AI 设计桌面应用，用自然语言驱动 agent 产出界面。本项目用它做三件事：

1. **设计系统变成"活资产"**：颜色、字号、间距、组件规范集中维护，可挂到 GitHub 做版本管理；还支持从网址、离线 `.fig` 文件或浏览器里截下的一页提取真实品牌规范（0.12 起）。这正好对上本项目的代码约定——颜色集中一处定义、深浅色模式自动切换。
2. **设计即代码，减少"设计稿 → 代码"的翻译损耗**：它产出的是 React + Tailwind 组件，与网页端 **Next.js 16 + Tailwind v4 + shadcn** 的技术栈同源，可直接复用；Flutter 端再按 Material 3 规范转译（画板仍按 390 × 844 出稿）。
3. **答辩与推广物料直接出厂**：支持把设计稿/牌组导出为真正的 PPTX、PDF（0.13 起），比赛用的设计说明、原型讲解页不必再手工排版。

工程侧要点：

- **开源、模型可以自己选**（填自己的模型密钥，也可以用官方托管的模型）；Windows 有便携版，与比赛机环境兼容，不依赖 macOS。
- 支持**插件与技能扩展**：我们把自己积累的"题库类界面规范"沉淀成插件，后续新页面按同一套风格生成，风格不漂移。
- **AI 产出仍需人工过一遍**：生成的代码只是初稿，最终以客户端架构检查脚本与网页端构建检查为准——设计可以 AI 生成，交付质量仍由人把关。

### 5. 设计稿与本项目代码的约定（保证设计稿能 100% 落地）

| 命令 | 断言内容 |
| --- | --- |
| `npm run test:pdf` | **37 项**：真实渲染一份 PDF 再用 pdfjs 抽回文字核对——中文折行不越版心（595.28−2×40）、行首禁则、**正卷绝不能出现答案**、图片嵌入比例、缺字自查 |
| `npm run test:phone` | **45+ 项**：手机号/合成邮箱的识别、格式化、折叠展示 |

#### 1.4 静态检查与架构守卫（质量不靠自觉）

- `flutter analyze` **零 error** 才算通过（CI 与本地同一口径）。
- `dart run tool/check_architecture.dart`（**0 = 通过**）是本项目自研的架构检查脚本，自动检查：单个文件不超过 200 行、代码分层与依赖方向正确（组件层不能直接访问接口与状态、页面模块之间不能互相引用）、每个界面文件只有一个公开类、字重只用常规 / 加粗两档、必须统一使用项目指定的界面组件库（用错来源会让页面切换动画莫名消失）。
- 网页端用 `npm run build` 做"能不能发"的硬门槛，构建失败即阻断发布。

#### 1.5 专项测试（这个产品的"高危点"清单）

1. **权限与越权**：学生不能看到没出分试卷的答案与选项分布（接口统一返回"无权访问"）；教师不能查看非本校、非本班数据；客户端对数据表只读、所有修改都走数据库函数——测试时**直接调接口**而不是点界面，证明拦截发生在数据库，而不是"把按钮藏起来了"。
2. **数据一致性**：三个以上连续下划线算一个空位（前后端同一规则）；多选判分比对**排序后的答案数组**（`['A','A']` 不等于 `['A']`）；空白字符判定用显式字符清单（客户端与数据库的正则范围并不完全相同）；"当天"一律按北京时间算，测试要跨零点验证。
3. **异常与弱网**：断网交卷、刷新中断、多标签页同时导入（另一个标签页正在处理这一页时，本页结果自动作废、不报错）、上游 AI 返回空内容（可重试）与返回非法 JSON（不可重试）必须区分。
4. **兼容性**：Android 多种 CPU 架构、Windows 1280×800 窗口、深色模式、超长题干与复合题材料排版、扫描件/图片题渲染。
5. **安全**：发布包必须是**正式签名**（CI 用 `apksigner verify` 拒绝 debug 签名）；密钥不入库、不进日志、不上报第三方。

#### 1.6 缺陷管理与回归

- 发现即开 **GitHub Issue**：复现步骤、期望结果、实际结果、截图/录屏、环境（系统/版本）、严重级别（P0 阻断主链路 / P1 影响功能 / P2 体验 / P3 建议）。
- 修复后**必须补一条自动化断言**（能自动化的一律不回退到人眼），再回归"该用例 + 同层级全量"。
- 每次发版前跑**冒烟清单**：主链路（出题→审批→组卷→考试→学生作答→出分→排行→资料下载）+ 下载页三资产名与 SHA-256 核对。

#### 1.7 准出标准（发布门槛，四条同时满足）

1. `flutter analyze` 零 error、`dart run tool/check_architecture.dart` 通过、`flutter test` 全绿。
2. 网页端 `npm run build` 通过 + `npm run test:pdf` / `test:phone` / `test:ai-report` / `test:retry` / `test:import` 全绿。
3. 集成测试 6 个场景在**待发布版本**上跑过（Windows 逐文件跑、Android 真机一遍）。
4. 无未关闭的 P0/P1 缺陷；已知问题有书面记录并明确"不影响发布"的理由。

#### 1.8 测试报告与复盘

每次发版输出一页报告：跑了什么（层级/数量）、通过了什么、发现并修了什么（按级别统计）、未覆盖的风险与原因、下次补什么。AI 负责**执行与汇总**，**通过/驳回与风险拍板由项目经理和指导教师签字**——AI 找 Bug，人决定能不能发。

## CI/CD运维、将错误上报到收集服务：Github Actions、Sentry

本岗位管两件事：**把代码稳定地变成学生能装的包**（CI/CD 持续集成、交付、运维），以及**让线上出的错自己飞回来**（错误上报到收集服务）。一次发布 = `git tag` 一个命令，从构建、签名、出包、分发到上线、监控全部自动完成。

### 1. 岗位职责（从一次提交到线上可用，再到出错可查）

#### 1.1 一条流水线跑完全程（GitHub Actions）

流水线在**客户端仓库** `mianyang_quiz/.github/workflows/release.yml`（约 500 行）；网页端没有自建工作流，构建与部署交给 Vercel（push 即构建）。

```mermaid
flowchart LR
  A["git tag vX.Y.Z<br/>git push origin --tags"] --> B{"release.yml"}
  B --> C["build-windows<br/>windows-latest"]
  B --> D["build-android<br/>ubuntu-latest"]
  C --> E["Release 资产<br/>固定名、不带版本号"]
  D --> E
  E --> F["镜像到阿里云 OSS<br/>client/ + latest.json"]
  F --> G["网页 /download<br/>5 分钟内自动更新"]
  E --> H["符号上传 Sentry<br/>崩溃栈可读"]
```

| 阶段 | 做什么 | 为什么这么做 |
| --- | --- | --- |
| **触发** | 打一个版本号 tag 就触发；也支持手动触发（只构建、不发布） | 一个 tag 出一个版本，安装包能对应到具体那次提交 |
| **并行构建** | Windows 与 Android 两台机器同时构建，Flutter 固定为 **3.47.0** | 两平台同时出包、环境完全一致，避免"我这能跑" |
| **版本号** | 用 tag 当版本号（去掉前面的 v），构建序号按流水线次数自动递增 | Android 只允许版本号更大的包覆盖安装，序号不递增用户会看到"应用未安装" |
| **注入配置** | CI 自动生成 `config/ci.local.json`（数据库地址、云存储地址、网站地址、错误上报地址） | 这些值会随安装包一起发出去（项目自带的公开密钥本来就打在包里），不算机密；**真正的密钥（云存储 AccessKey、AI 密钥）只存在服务端** |
| **出包** | Windows → 绿色包 zip + 安装程序 setup.exe；Android → 按 CPU 架构拆成三份 APK（新手机 / 老设备 / 模拟器） | 一个通用安装包里塞了三套原生库，其中两份对任何一台机器都用不上，白占下载流量 |
| **守门** | 没有正式签名 → 打 tag 直接失败；构建前先校验签名文件，构建后回头检查产物签名，发现是"调试签名"就判失败；三份 APK 少一份也算失败 | 调试签名能装能跑，但签名随构建机变化，老用户下一版就装不上；少一份 APK 就是"老设备点下载 404" |
| **发 Release** | 两个平台都构建成功、且确实是打 tag 触发的，才发布版本 | 任一平台失败则整个版本不发布，不做"半套包" |
| **镜像到国内 OSS** | 把安装包复制一份到国内云存储，并写一份版本清单；没配密钥不算失败 | 国内直连 GitHub 实测 20 秒拿不到一个字节，镜像到成都云存储后 7~9.6MB/s；没配就退回慢线路 |
| **上线** | 网页下载页读取版本清单 `latest.json`（每 5 分钟自动刷新一次） | 客户端先发、网页端 5 分钟内自动跟上，不用手动改链接 |

> 资产名**固定不带版本号**（`mianyang_quiz-android.apk`、`mianyang_quiz-windows-x64.zip`、`…-setup.exe`），这样"下载最新版"的地址可以写死不变，网页与客户端都不必跟着版本改。**资产名两端逐字一致**——网页端 `app/download/page.jsx` 的常量与客户端 `tool/upload_to_oss.mjs` 推上去的是同一套，改一处必须改另一处，否则点下去就是 404。

#### 1.2 CI：每次提交的自动闸门

- **客户端三条全过才算改完**：`flutter analyze` 零 error、`flutter test` 全绿、`dart run tool/check_architecture.dart` 通过。只跑 `flutter analyze` 不够——测试里锁着判分规则（"客户端提前判分"和"服务端权威判分"必须得出同一个结果）。
- **网页端**：`npm run build`（能不能发的硬门槛）+ `npm run test:*`（PDF 37 项检查、手机号 45+、AI 报告 11 项、重试安全性、导入流水线）。
- **一票否决**：任何一项红都不合入。原则是"提交前本地跑一遍"，CI 是复核而不是第一道防线。

#### 1.3 CD：可重复、可回滚、可兼容

- **构建可重复**：Flutter 版本固定；配置由流水线注入、不进代码仓库（本地配置文件只放在各人自己电脑上）。
- **回滚**：网页端在部署平台一键回滚到上一版；客户端回滚 = 把版本清单和发布页指回旧安装包（资产名固定，所以回滚只是换文件）。
- **数据库只往前走**：改表时先加新字段、等旧版本用户升级完再删旧字段（先兼容、后清理），并且必须兼容**还装着旧版本包**的学生——他们不会立刻升级。已经执行过的破坏性改动没有自动回滚，只能"再写一个迁移改回来"。
- **发布说明必须写清**：换签名、换安装包架构的版本要先卸载再装（Android 不允许覆盖安装），否则那批用户会卡在"应用未安装"。

#### 1.4 运维：可用性、成本与配置

| 维度        | 做法                                                                | 原因                                                            |
| --------- | ----------------------------------------------------------------- | ------------------------------------------------------------- |
| **区域**    | 网页服务器在香港、数据库在东京、文件存储在成都                    | 离用户近，跨区访问少，首屏更快                                               |
| **域名与代理** | `api.myquiz.cn` 由一个只替换域名的反向代理（Cloudflare Worker，`supabase-proxy/`）转发 | 国内部分线路直连数据库域名时加密连接会被中途切断，表现成"网络连接失败"且时好时坏      |
| **缓存**    | 网页本身一页都不缓存；页面数据每 5 分钟刷新一次；图片交给云存储自带的图片处理        | 缓存网页会让不同账号看到彼此的页面（登录后串号）                                         |
| **密钥**    | 全放在 GitHub Secrets / Vercel / Supabase 的密钥配置里；客户端只带公开密钥      | 代码混淆只是改名字、挡不住有心人，**密钥永远不许放进客户端**                                  |
| **下载线路**  | 安装包 exe/zip 走自家成都云存储；APK 走 GitHub 加速镜像，页面上印出校验码 SHA-256 供核对               | 云存储服务商不允许 `.apk` 从默认域名分发（会被直接拒绝），由服务器代为下载同样被拦 |
| **值班与响应** | 学生反馈 → 复现 → 热修打新 tag（客户端不能热更）或网页热回滚                               | 客户端只有"发新版本"这一条路，所以每次发版都要留回滚预案                                 |

#### 1.5 错误上报到收集服务：Sentry

**为什么必须有**：学生端装在机房电脑和随身手机上，崩了只会说"打不开 / 闪退"。老师无法复现、更拿不到堆栈——没有上报就是盲修。

**接的是什么**：Flutter 的错误上报库 `sentry_flutter`，版本 **10.0.0-rc.1**（10.x 系列）。

> 为什么不用更早的稳定版：9.30.1 在 Windows 上编译不过（依赖的 C++ 头文件写法不被微软工具链接受），8.14.2 在 Android 上编译不过（构建工具版本对不上），10.x 才做到两个平台都能出包。

代价：它要求 **Android 8.0 及以上**，不再支持 Android 7.x 及以下——这条要写进产品说明。

**只报"没见过的错"**：两类错误分开处理，否则网络抖动会把真正的问题淹掉。

| 哪一类 | 走什么 | 用户看到 | 上报？ |
| --- | --- | --- | --- |
| 预期内的失败（网络断、登录过期、服务端拒绝） | 统一的错误转换，转成一句中文提示 | 一句中文提示 + 重试 | **不上报** |
| 没被接住的（页面构建时抛的、异步忘了 catch 的） | 全局异常处理（三个钩子） | 那块内容变成一句「没能显示出来」 | 上报 |

三个钩子全在 `lib/error_handling.dart`，由 `main.dart` 在 `runApp` **之前**安装：

1. `FlutterError.onError` —— 页面构建 / 布局 / 绘制阶段抛出的异常；
2. `PlatformDispatcher.instance.onError` —— 异步代码里没人处理的错误。**必须返回 `true` 表示"我处理了"**，返回 `false` 会让系统走兜底路径，发布版可能直接结束进程——用户看到闪退，我们连一行日志都留不下；
3. `ErrorWidget.builder` —— 某块界面构建失败时画什么。**必须做尽可能少的事**（框架此时可能已经不稳定），只返回最基础的文本组件；测试里还故意不给它任何外层环境（没有主题、没有页面容器）验证它照样画得出来。

两条铁律：先装全局异常钩子、再初始化上报库（上报库会包装现有的钩子，顺序反了钩子会被顶掉）；**钩子里绝不能再调上报库**，否则同一条错误报两次。

**隐私是硬红线**（这是未成年学生的数据，四个开关显式关掉而不"靠默认值"）：

| 选项 | 为什么关 |
| --- | --- |
| `attachScreenshot` | 截图里有题干正文与学生的真实姓名 |
| `attachViewHierarchy` | 视图树里同样有 |
| `enablePrintBreadcrumbs` | **默认是开的**，会把所有 `debugPrint`（启动失败详情、题目 id）收成面包屑 |
| `sendDefaultPii` | 关掉身份信息 |

**让堆栈可读**：发布包做了代码混淆，符号文件与名字映射表**只作为流水线产物归档、绝不放进发布页**（它们能把混淆后的名字还原，公开挂着等于没混淆）；流水线用密钥 `SENTRY_AUTH_TOKEN` 把符号传给错误收集服务——没配就跳过（不阻塞发版，只是看到的堆栈是乱码）。

**没配上报地址（`SENTRY_DSN`）就整个是空操作**：不初始化、不发任何请求，开发机与 CI 都不配它。上报地址与上传密钥是上线前要补的两个配置。

**上报是"尽力而为"**：2026-09-28 在本机实测能连通错误收集服务（域名解析正常、加密连接 0.3 秒、真实上报一条记录返回成功），但上报库遇到网络问题会自己忽略，发不出去也绝不影响软件的任何功能。留个心眼：本项目已经因为"境外域名不通、调用又没设超时"踩过一次坑——PDF 中文字体原先从境外字体站拉取，点「打印」既不报错也不弹窗，师生的感受就是"按钮没反应"。**学生所在的网络与开发机不是一回事**，要真依赖某个域名，先去目标网络实测。

**当前边界（如实说明）**：网页端尚未接入 `@sentry/nextjs`，目前靠 Vercel 构建/运行日志 + 数据库审计日志 + 用户反馈兜底；接入 Sentry Web 已列为下一步。

#### 1.6 发布检查单（每次发版逐条打勾）

- [ ] 三条静态/测试门槛全绿（analyze / test / check_architecture；网页端 build + test:*）
- [ ] 集成测试在**待发布版本**上跑过（Windows 逐文件跑，Android 真机一遍）
- [ ] Android 用正式签名（CI 的 `apksigner verify` 已回头看）；首次换签名的版本在说明里写"需先卸载"
- [ ] 三份 APK 与 Windows 两个包都在 Release 里，资产名与网页端常量逐字一致
- [ ] 网页 `/download` 的版本号、SHA-256 与新包一致（镜像后 5 分钟内核对一次）
- [ ] 符号文件已归档（artifact + 本地各一份），Sentry 能看到新版本的符号
- [ ] 发布说明写明：版本号、主要变更、已知问题、回滚方式
- [ ] 上线后 10 分钟盯一眼：Sentry 有无新增崩溃、用户反馈与审计日志有无异常
