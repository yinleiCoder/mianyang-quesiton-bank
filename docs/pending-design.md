## 一、多市区（四川省下的市）

### 查证过的事实

- **`school_id` 是全库唯一的租户锚点**，8 张表挂在它上面：
  `profiles` / `questions` / `papers` / `classes` / `review_materials` /
  `import_jobs` / `approval_inbox` / `approver_assignments`
- **`city_id` 一处都不存在**（`information_schema.columns` 查过）
- `schools` 只有 `id, name, code, is_active, created_at, updated_at` —— **没有市这一列**
- **迁移文件里零处市名**，所以"现在只有绵阳"是靠**数据**实现的，不是靠 schema

### 决定

```
新增 cities（超管维护）
  └─ schools 加一列 city_id          ← 只加这一列，其余全部**推导**
```

"这个人在哪个市" = `profiles.school_id → schools.city_id`，一次 join。

**不要在 `questions` / `approvals` 上各加一列** —— 那要改几十个查询，
还多一份可能不一致的状态。

### 用户逐条拍板的口径

| 问题 | 答案 |
|---|---|
| 跨市题目能不能改 | **只能申诉**，见第二节。修改权不变 |
| 一人能否是多市专家 | **不能**。这条**不用加约束**：人的市由 school 推导，天然互斥 |
| 谁建市、谁建校 | **超管**。学校的具体事务仍下放给学校管理员 |
| 省级要不要审核 | **不要**。审核只到市级那一层 |
| 题库 | **全省共享**（读路径本来就没有市过滤，不用改） |

### 执行顺序

1. `cities` + `schools.city_id`（纯增量，**不动任何现有 RLS**）
2. 验证"超管建市 → 建校 → 教师落在哪个市"这条链
3. 再动市级审批池的市域收口

**只做第 1 步也不会留下半成品**，这是刻意选的切入顺序。

## 二、题目申诉机制（**不是**修改机制）

### 用户的原话与纠正

> 跨市修改：应该不是修改，而是申诉，原本题目就缺少申诉机制。修改应该发起打回，
> 申诉是和出题人及审题人进行沟通，**修改和撤回的权限还是应该沿用审核机制，
> 其他老师只有申诉权，没有直接修改权**。

**这一条让方案安全了很多**：原方案是"放开 RLS 让任何教师可改"，
那会动审批链的核心假设；改成只加申诉权之后，**整个功能是纯增量的**——
现有 RLS 与审批流一行不改。

### 查证过的事实

`question_reports` 现有列：
`id, question_id, version_id, reporter_id, category, content, status,
resolve_note, resolved_by, resolved_at, created_at, updated_at`

**它是单向的**：一条举报 + 一条处理说明，**没有往来**。
而申诉要的是"和出题人及审题人**沟通**"——缺的是多方对话。

### 决定

**接在 `question_reports` 上，不另起一张表**（数据模型 90% 重合，
另起一张要把 `version_id` 之类的教训再踩一遍）。补两样：

**① 多方对话**

```
question_report_messages(
  report_id, author_id, body, created_at
)
```

**② 可见性扩到三方**：申诉人 / 本题出题人 / 本题的**审题人**

现在大概是"reporter 或本题作者"。教师身份不用加列——
`profiles.identity` 已经区分了。

**③ 出口接回现有审批链**

申诉本身**不产生任何修改**。终态三种：

- `rejected` —— 说明理由
- `accepted` —— **触发打回**，题回到作者手里**重走现有审批**
- `withdrawn` —— 申诉人自己撤回

"打回"复用现有 RPC，**不新开改题路径**。

> **这条设计的全部价值**：它没有新增任何一条能改到已发布内容的路径。
> 申诉只是"说"，改还是原来那条链。评审时如果发现有人想从申诉这条路
> 绕过去改题，那就是设计被破坏了。

## 三、协同组卷

### 用户的原话与纠正

> 标记组卷创始人，该创始人可以邀请其他老师共同组卷。
> 用**户纠正**：方案可以，但是一套卷子**不应该下放到大题之间**，
> 而是每个大题下面的**每道题都可能是不同的老师**，
> 所以这时候创始人应指定**分派子卷题号及分值任务**。

（原方案是按大题认领，被否了。）

### 决定：分卷 + 合卷，**不做实时协同**

理由：实时协同（CRDT）解决的是"两个人同时改同一个字"；
但组卷的真实瓶颈**不是编辑冲突，是工作量**——一套卷 30 道题要一道道挑。
两位老师同时改同一道题的标题，现实中几乎不会发生。

分卷合卷把工作量切开，**冲突面从"每道题"降到"任务段之间"**，
而任务段天然不重叠。

### 分派单元 = 大题内的**题号区间 + 分值**

```
paper_assignments(
  paper_id, section_id,
  from_qno, to_qno,      -- 题号区间，如「大题三 第 3~7 题」
  score,                 -- 这段占多少分，如 20
  assignee_id,
  state                  -- open / claimed / submitted / locked
)
```

- 创始人的动作是**划任务**：「大题三、第 3~7 题、20 分、给张老师」
- 老师只看到分给自己的那几段空位
- **交了即锁**（`submitted` → `locked`），要改得创始人解锁
  —— 这条比乐观锁更简单，也更贴合"限时完成"的场景
- `papers.owner_id` = 创始人，持有**合卷视图**：各段状态一屏铺开

### 为什么不用乐观锁就够

乐观锁处理的是"两个人改同一处、后保存的发现冲突"。
但这里同一段本来就只分给一个人，冲突根本不会发生。
**锁的作用是防"交完又被改"，不是防并发写。**

## 四、执行顺序建议

1. **多市区**：`cities` + `schools.city_id`（纯增量，可独立验证、可回退）
2. **申诉机制**（纯新增表 + RPC，不动现有权限）
3. **协同组卷**（新表 + 分派界面 + 合卷视图，双端）

每一步都能独立上线、独立回退。**不要并行做**——它们都动审批与权限，
出问题时无法归因。
